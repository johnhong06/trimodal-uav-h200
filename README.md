# trimodal-uav-h200

RGB · 열화상 · 이벤트 카메라 세 가지로 UAV 영상에서 차량을 찾는 논문, *Tri-Modal Fusion Transformers for UAV-based Object Detection* (arXiv 2604.16630) 을
**논문과 같은 데이터 · 같은 분할**로 다시 학습해서 논문 수치 (MiT-B1, mAP 84.24) 를 넘을 수 있는지 보는 실험 묶음이다.
Aerodrone H200 에서 돌리려고 만든 공개 저장소다.

이 저장소에는 우리 코드와 작은 목록 (분할 · 통계 · 체크섬) 만 있다. 저자 코드 · 데이터셋 · 사전학습 가중치는 작업이 시작할 때 원래 자리에서 받는다.

## 왜 하나

논문은 열화상 · 이벤트 두 채널을 한 줄기로 묶고 RGB 줄기와 백본 네 stage 에서 섞는다 (MAGE + BiTE). 같은 데이터에서 융합 방식 · 위치 · 백본 크기를 61 가지로 비교했다.
저자 코드 (radlab-sketch/trimodal-uav-det @ e1d2dede) 를 읽어 보면 기준선이 기본 설정부터 약하다.

- 백본을 사전학습 없이 처음부터 학습한다. 이 코드의 융합 모듈 원본인 CMX 는 ImageNet 사전학습 가중치를 쓴다.
- 입력을 255 로 나누지 않는다. 0–255 값을 0–1 용 평균 · 표준편차로 정규화해서 RGB 는 최대 약 1,100 까지 들어간다.
- Faster R-CNN 기본값 때문에 사진 (301×391) 을 약 2.66 배 키워서 학습 · 평가한다. 논문에는 원본 해상도라고 적혀 있다.
- 데이터 증강이 없다.

또 mAP50 은 98.95 인데 mAP (IoU 0.50–0.95) 는 84.24 다. 차는 거의 다 찾고 점수는 엄격한 IoU 에서 박스 위치가 조금씩 어긋나는 데서 잃는다는 뜻으로 읽힌다 (실험 1 에서 확인한다).
그래서 기본 설정을 먼저 바로잡아 기준선을 세우고, 그 위에 작은 보정 모듈 두 개를 붙여 본다.
하나는 두 줄기를 섞기 직전에 픽셀마다 어느 줄기를 얼마나 믿을지 고치고 (A), 다른 하나는 픽셀별 경계 맵으로 박스의 변을 고친다 (B).
큰 인코더를 덧붙이지 않고 검출기가 이미 만든 특징만 쓴다.

## 공통 설계

- **분할은 저자와 같다.** 저자 코드 그대로 라벨이 있는 9,750 장을 `train_test_split(test_size=0.2, random_state=42)` 로 나눈다 → train 7,800 · test 1,950.
  작업 안에서 저자 Dataset 으로 다시 나눠 `splits/author_split.csv` 와 같은지 확인한다. **최종 숫자는 test 1,950 장에서만 낸다.**
- **설정은 검증 세트로만 고른다.** 저자 코드는 검증 세트 없이 test 로 평가한다. 우리는 train 안에서 낮 · 밤마다 10 % (780 장) 를 떼어 검증 세트로 쓴다. test 로는 아무것도 고르지 않는다.
- **학습 일정은 저자와 같다.** 15 epoch · 배치 16 · 500 스텝 warmup 뒤 cosine · AMP 없음 · 마지막 epoch 의 모델을 쓴다 (고르지 않음).
  저자 코드 (MiT · MAGE · BiTE · FPN · Faster R-CNN 설정) 는 고치지 않고 불러 쓴다. 바꾸는 것은 실험마다 아래 표에 적은 것뿐이다.
- **지표도 저자와 같다.** torchmetrics `MeanAveragePrecision` (COCO 방식). 전체 · 낮 · 밤을 따로 잰다. 숫자는 % 로 적는다.
- **시드 3 개 (0 · 1 · 2).** 논문 안의 차이가 1 점 안팎이라 한 번 돌린 숫자로는 비교할 수 없다.
- 데이터: 사진 10,489 장 중 라벨이 있는 9,750 장을 쓴다 (낮 3,339 · 밤 6,411). 차량 박스 30,634 개, 한 클래스.

## 실험 2 — 기본 설정 보강

### 설계

- 사전학습 가중치와 입력 정규화를 바로잡는다 (팔 `base`). 사전학습 백본에는 저자의 SGD 0.02 가 너무 클 수 있어서 최적화를 하나 고른다.
- 고르기: train 에서 검증 780 장을 뺀 7,020 장으로 SGD (lr 0.02 · momentum 0.9 · wd 1e-4) 와 AdamW (lr 1e-4 · wd 0.05) 를 시드 0 으로 한 번씩 학습하고 검증 mAP 를 본다.
- 고른 최적화로 train 7,800 장 전체에서 시드 3 개를 학습해 test 에서 잰다.

### 판정 기준 (2026-11-11, 결과 전에 고정)

- **고르기**: AdamW 의 검증 mAP 가 SGD 보다 0.3 이상 높으면 AdamW, 아니면 SGD (저자 최적화).
- **개선 판정** (실험 2 · 3 공통): Δ = 두 팔의 시드 평균 차, 폭 = 두 팔 각각의 시드 범위 (최댓값 − 최솟값) 중 큰 것.
  Δ > 폭 이면 **개선**, 0 < Δ ≤ 폭 이면 **약한 개선**, Δ ≤ 0 이면 **개선 없음**.
- `base` 는 `paper` 재현과 비교한다. 이것은 우리 방법의 성과가 아니라 기준선을 바로 세운 효과로 따로 적는다.

## 실험 3 — 우리 방법: 픽셀별 보정 모듈 두 개

### 설계 (2026-11-12 에 다시 정함)

처음 설계는 고정 DINOv2-L (304 M) 의 특징을 FPN 에 더하는 것이었고 돌리기 전에 접었다.
60 M 짜리 UAV 검출기에 다섯 배 큰 인코더를 붙이면 추론이 28 ms 에서 80 ms 로 늘어난다 (smoke 에서 잰 값). 그렇게 올린 mAP 는 의미 있는 개선으로 보기 어렵다.
그 코드는 커밋 a8bb505 까지 남아 있다. 새 설계의 조건은 이렇다.

- 인코더를 더 붙이지 않는다. 모듈의 입력은 검출기가 이미 만드는 특징뿐이다.
- 모듈 하나의 학습 파라미터는 1 M 미만이다. 늘어난 파라미터와 추론 시간을 표에 같이 적는다.
- 꼴은 TR2M 에서 가져왔다. TR2M 은 작은 어텐션 모듈이 픽셀별 scale · shift 맵 두 장을 내서 상대 깊이를 절대 깊이로 고친다. 여기서도 작은 어텐션 모듈이 픽셀별 보정 맵을 내고 그 맵으로 검출기가 이미 낸 값을 고친다.
- 두 모듈 모두 보정이 0 에서 시작한다. 학습 첫 순간의 출력은 `base` 와 똑같다 (`tests/test_parts.py` 가 확인).

**A — 융합 보정 (`fuse`, `src/rescale.py`, +0.50 M)**

- 고치려는 것: 저자 융합은 stage 마다 MAGE 가 두 줄기에 서로의 특징을 더해 주고 BiTE 가 둘을 하나로 합친다. MAGE 는 더하기만 해서 믿기 어려운 줄기를 줄이지 못한다. 밤의 RGB (밝기 중앙값 18.9/255) 가 그런 줄기다.
  MAGE 의 채널 가중치는 사진 한 장에 값 하나이고 공간 가중치는 1×1 conv 라 그 픽셀만 본다.
- 방법: BiTE 에 들어가기 직전의 두 줄기를 네 stage 모두에서 픽셀마다 `x' = γ ⊙ x + β` 로 고친다.
  - 두 줄기를 stride 16 격자로 줄여 64 채널로 만들고 교차 어텐션으로 서로를 본다 (Q = 자기 줄기, K · V = 상대 줄기, 양방향).
  - 1×1 conv 가 [자기 특징 ; 같은 자리의 상대 특징 ; 어텐션 결과] 에서 γ (픽셀별 1 채널, 0–2) 와 β (채널마다) 를 낸다. 처음에는 γ = 1, β = 0 이다.
  - 다음 stage 로 가는 두 줄기는 고치지 않는다. 사전학습 백본이 받는 입력을 `base` 와 같게 두려는 것이다.
- 기존과 다른 점: 곱하기라서 한 줄기를 줄일 수 있다. 그리고 그 픽셀 하나가 아니라 같은 자리의 상대 줄기와 장면 전체를 보고 정한다.

**B — 경계 보정 (`edge`, `src/edge.py`, +0.14 M)**

- 고치려는 것: 저자 검출기는 후보 박스마다 7×7 격자로 특징을 뽑고 FC 2 층이 보정값 4 개를 한 번에 낸다. 차 한 대 (원본에서 한 변 약 52 px) 에 격자 한 칸이 약 7 px 다.
  IoU 0.9 를 넘으려면 변마다 1–3 px 안에 맞아야 한다. 재현에서 mAP50 은 98.3 인데 mAP 가 85.5 인 것과 맞는 이야기다.
- 방법: 가장 고해상도 FPN 층 (stride 4, 원본으로 약 1.5 px) 에 작은 모듈을 붙여 픽셀별 경계 맵을 낸다. 픽셀마다 자기를 담은 차의 왼 · 위 · 오른 · 아래 변의 좌표 4 장과 신뢰도 1 장이다.
  - 모듈은 1×1 conv 로 64 채널로 줄인 뒤 [가로줄 어텐션 → 세로줄 어텐션 → conv] 를 두 번 한다. 박스의 변은 축에 나란해서 같은 가로줄 · 세로줄만 보면 된다. 픽셀이 5 만 개가 넘어도 줄 단위라 어텐션이 싸다.
  - 변의 좌표는 숫자로 회귀하지 않는다. 변마다 어텐션이 같은 줄에서 변이 놓인 칸을 가리키고 그 칸의 좌표를 읽는다 (soft-argmax). 3×3 conv 가 칸 안의 작은 보정값을 더한다.
    가짜 특징으로 이 모듈만 학습시켜 보니 거리를 회귀하는 머리보다 이쪽이 빨리 배웠다 (`tools/sanity_edge.py`: 1,400 스텝 뒤 투표의 변 오차 2.36 px vs 3.94 px, 흔들어 준 박스의 오차는 3.0 px).
  - 박스 가운데 절반 영역의 픽셀들이 말한 변의 좌표를 신뢰도로 가중 평균한다. 이것이 투표다.
  - `변 ← 변 + g · c · (투표 − 변)`. g 는 0 에서 시작하는 학습 스칼라, c 는 그 영역의 평균 신뢰도다. 맵이 확신하지 못하는 곳의 박스는 움직이지 않는다.
    화면 끝에 닿은 변도 그대로 둔다 (박스의 약 30 % 가 화면 가장자리에 걸려 있다).
  - 손실 세 개를 더한다. 픽셀이 말한 변과 정답 변의 오차, 신뢰도가 그 픽셀 박스의 IoU 를 맞히게 하는 손실 (quality focal loss), 보정한 박스와 정답의 변 오차다. 변 오차는 박스 크기로 나눈다.
    변 오차 손실의 기울기는 박스 헤드로 가지 않게 끊는다. 박스 헤드는 `base` 와 같은 손실로만 학습한다.
  - 추론에서는 NMS 뒤 최종 박스에만 적용하고 점수는 바꾸지 않는다.
- 기존과 다른 점: 박스를 정하는 해상도가 7 px 격자에서 1.5 px 픽셀로 바뀐다. 보정값을 한 번에 내지 않고 박스 안 픽셀들이 변마다 투표한다.
- 비슷한 선행 연구가 있다. 픽셀마다 박스의 네 변을 예측하는 것은 FCOS, 박스 안 여러 점의 예측을 모으는 것은 D2Det, 변 단위 위치 추정은 SABL, 변의 위치를 분포의 기댓값으로 읽는 것은 GFL 이 먼저 했다.
  여기서는 그 투표를 2 단계 검출기의 최종 박스에 사후 보정으로 얹고 맵을 축 어텐션으로 만든다. 이 방법들과 직접 비교하는 실험은 이번 묶음에 없다.

**A + B (`both`)**

- A 는 백본의 융합 단계를, B 는 박스 헤드를 바꾼다. 겹치는 곳이 없어서 그대로 같이 넣는다.
- 효과는 겹칠 수 있다. A 가 밤 사진의 박스 위치까지 고치면 B 의 몫이 줄어든다. 그래서 둘의 향상을 더해서 어림하지 않고 따로 학습해서 잰다.

**학습**

- 본체는 `base` 와 같은 최적화로 학습한다 (실험 2 에서 고른 것). 우리 모듈만 따로 AdamW lr 1e-3 · weight decay 0.05 로 같이 학습한다. warmup 과 cosine 일정은 본체와 같다.
  처음부터 학습하는 작은 어텐션 모듈이라 본체의 값으로는 느리게 배운다. 위 합성 실험에서 SGD 0.02 는 같은 스텝에 변 오차가 3.23 px 였다.
- 모듈 값은 결과 전에 고정했고 검증 세트로 고르지 않았다: 폭 64 · 어텐션 헤드 4 · B 의 블록 2 개 · 투표는 박스 가운데 절반을 7×7 로 · 손실 가중치는 모두 1. 결과가 좋으면 ablation 은 그 뒤에 한다.
- 합성 실험은 B 의 머리 구조와 모듈의 학습률을 고르는 데만 썼다. 실제 데이터에서 B 가 박스를 더 정확하게 만드는지는 작업 C 가 답한다.

### 판정 기준 (2026-11-12, 결과 전에 고정)

- `fuse` vs `base`, `edge` vs `base`: 모듈 하나의 효과다. 실험 2 의 개선 판정 규칙을 그대로 쓴다.
- `both` 는 `fuse` 와 `edge` 의 시드 평균이 둘 다 `base` 보다 높을 때만 돌린다. `both` 가 둘 중 평균이 높은 쪽과 비교해서도 개선이어야 "합칠 가치가 있다" 고 적는다.
- **논문을 넘음**: `both` → `fuse` · `edge` 중 평균이 높은 것 → `base` 순서로 본다. 시드 평균 mAP > 84.24 이고 `paper` 대비 판정이 개선인 첫 번째를 적는다.

- 예상도 미리 적어 둔다. 판정에는 쓰지 않고 맞았는지만 결과에 적는다.
  - A 가 생각대로 작동하면 `base` 대비 밤 mAP 가 낮 mAP 보다 더 오른다.
  - B 가 생각대로 작동하면 `base` 대비 mAP75 가 mAP50 보다 더 오르고 오차 분해에서 IoU 0.9 로 찾은 비율이 오른다.

## H200 실행

요청 이슈에 명령 한 줄을 적는다 (`bash run.sh <모드> KEY=값 …`). GPU 할당량은 `7` (H200 한 장).

| 순서 | 이슈 명령 | 할당량 | 하는 일 |
|---|---|---|---|
| 1 | `bash run.sh check` | `1` | 1–2 분. 경로 · 공간 · GPU · 외부 접속 확인 (Google Drive 포함). 아무것도 설치하지 않음 |
| 2 | `bash run.sh smoke` | `7` | 모든 단계를 아주 작게 (학습 64 장 · 평가 64 장 · 1 epoch). 환경 만들기 · 데이터 받기 포함 |
| 3 | `bash run.sh all` | `7` | 실험 0 · 2 · 3 전부 (학습 18 번) 와 표 · 판정. 실제로는 아래처럼 나눠서 낸다 |

- `smoke` 는 2026-11-11 H200 에서 11 분에 끝났다 (환경 만들기 · Drive 에서 받기 2.1 분 · 풀기 36 초 포함).
  GPU 최대 메모리는 학습 하나에 71 GiB 라서 한 장에 하나씩만 돈다.
- 스텝당 시간은 작업 A 1 차에서 다시 쟀다. 저자 스크립트가 15 epoch (7,320 스텝, 배치 16) 을 94 분에 끝냈으니 스텝당 0.77 초다.
  smoke 에서 잰 1.04–1.11 초는 4 스텝 값이라 초반 준비 시간이 섞여 있었다. 우리 `paper` 학습도 0.76 초였다 (작업 A).
- 학습 하나는 약 1.6 시간 (고르기는 약 1.4 시간) 이다. 모듈을 붙인 팔은 아직 재지 않았고 5–15 % 더 걸린다고 어림했다.
- 작업을 나눠서 낸다. 앞 작업의 결과를 보고 다음 작업을 정하려는 것이다.

  | 작업 | 이슈 명령 (할당량 `7`) | 어림 시간 |
  |---|---|---|
  | A | `bash run.sh all ARMS=author,paper` | 6.4 시간 (끝남) |
  | B | `bash run.sh all ARMS=select,base` | 약 7.5 시간 |
  | C | `bash run.sh all ARMS=fuse,edge OPT=<B 에서 고른 값>` | 약 11 시간 (어림) |
  | D | `bash run.sh all ARMS=both OPT=<B 에서 고른 값>` | 약 6 시간 (어림). C 의 결과가 실험 3 의 조건을 채울 때만 |

  A 와 B 는 서로 기대지 않는다. C · D 는 B 의 화면에 나오는 `[select] … → sgd|adamw` 값을 `OPT=` 로 넘긴다 (작업끼리는 파일이 이어지지 않음).
  C 를 내기 전에 `bash run.sh smoke ARMS=fuse,edge,both OPT=sgd` (약 10 분) 로 새 팔의 GPU 메모리와 스텝 시간을 먼저 잰다. 모듈의 어텐션이 메모리를 얼마나 더 쓰는지는 아직 재지 않았다.
  작업들의 `results.zip` 은 로컬에서 `runs/` 를 한 폴더에 모아 `python src/report.py summary --runs <폴더> --out <폴더>` 로 한 표로 합친다.
- 결과는 `/app/output/<작업>/results.zip` 하나다 (경로는 화면 첫 줄과 마지막 줄에 나온다). 이슈 번호와 이 경로를 적어 관리자에게 요청한다.
